Multi-stage targeted Docker builds: smaller images, faster deploys

How to use multi-stage builds and build targets to cut your production image size dramatically and stop shipping your dev dependencies to production.

A Node.js app with a naive Dockerfile will produce an image north of 1 GB. The same app with a properly structured multi-stage build lands under 200 MB. That's not a rounding error - it's the difference between a 90-second deploy and a 15-second deploy, and between a container that exposes a full build toolchain and one that contains only what needs to run.

This is the pattern I use on every project now. It took me longer than it should have to learn it properly, so here's the version I wish someone had shown me.

What single-stage builds get wrong

The typical first-pass Dockerfile looks something like this:

# The naive approach
FROM node:20

WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

CMD ["node", "dist/index.js"]

This works. But the final image contains:

  • The full Node.js runtime and all of npm
  • Every dev dependency - TypeScript, ts-node, Jest, ESLint, all of it
  • Your source files, not just the compiled output
  • The entire build toolchain that compiled your code

You ship all of that to production, on every deploy, through every environment. It sits in your container registry eating storage. It gets scanned for vulnerabilities. And none of it needs to be there.

Multi-stage builds: the concept

A multi-stage Dockerfile is a single file with multiple FROM instructions. Each FROM starts a new stage with its own filesystem. Crucially, you can copy specific files between stages - and only those files end up in the final image.

The build stages are ephemeral. Docker uses them to produce the output you need, then discards them. Your final image only contains what you explicitly copy into the last stage.

A production-ready Node.js Dockerfile

# ── Stage 1: install dependencies ─────────────────────
FROM node:20-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci --frozen-lockfile

# ── Stage 2: build ─────────────────────────────────────
FROM node:20-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

# ── Stage 3: production runtime ────────────────────────
FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production

# Only copy production deps and compiled output
COPY package*.json ./
RUN npm ci --frozen-lockfile --omit=dev

COPY --from=builder /app/dist ./dist

EXPOSE 3000
CMD ["node", "dist/index.js"]
Single-stage

~1.1 GB - full Node image, all deps, source files, build tools

Multi-stage

~180 MB - Alpine base, prod deps only, compiled output only

A few things worth calling out:

  • node:20-alpine instead of node:20: Alpine Linux is a minimal distro. Switching base image alone drops ~600 MB. Use it in every stage unless you have a specific reason not to.
  • npm ci --frozen-lockfile: faster than npm install, deterministic, and fails loudly if package-lock.json is out of sync - exactly what you want in CI.
  • Separating deps from builder: Docker layer caching means the npm ci step only re-runs when package*.json changes. Source code changes don't invalidate the dependency layer.

Build targets: one Dockerfile for every environment

This is where it gets powerful. Instead of maintaining separate Dockerfiles for dev and production, use named targets in a single file and build to whichever stage you need.

# ── Stage 1: base ──────────────────────────────────────
FROM node:20-alpine AS base
WORKDIR /app
COPY package*.json ./

# ── Stage 2: dev ───────────────────────────────────────
FROM base AS dev
RUN npm install
COPY . .
CMD ["npm", "run", "dev"]   # hot reload, source maps, all dev tooling

# ── Stage 3: test ──────────────────────────────────────
FROM base AS test
RUN npm install
COPY . .
CMD ["npm", "run", "test"]  # run once, exit  - used in CI

# ── Stage 4: builder ───────────────────────────────────
FROM base AS builder
RUN npm ci --frozen-lockfile
COPY . .
RUN npm run build

# ── Stage 5: production ────────────────────────────────
FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --frozen-lockfile --omit=dev
COPY --from=builder /app/dist ./dist
EXPOSE 3000
CMD ["node", "dist/index.js"]

Now you can target exactly the stage you need:

# Local development (hot reload, full deps)
docker build --target dev -t myapp:dev .

# Run tests in CI (same environment, deterministic)
docker build --target test -t myapp:test .
docker run --rm myapp:test

# Production deploy (minimal, hardened)
docker build --target runner -t myapp:prod .
docker push myapp:prod

One Dockerfile. Every environment. No drift between what you test locally and what runs in production.

Layer caching in CI: the detail that makes deploys fast

Multi-stage builds only help if Docker's layer cache is warm. In CI, the cache is cold on every run by default - which means all that work structuring your stages gets thrown away.

The fix is inline cache (or registry cache, depending on your setup). With GitHub Actions and BuildKit:

# .github/workflows/deploy.yml
- name: Build and push
  uses: docker/build-push-action@v5
  with:
    context: .
    target: runner
    push: true
    tags: ${{ env.IMAGE_TAG }}
    cache-from: type=gha
    cache-to: type=gha,mode=max

The type=gha cache stores layer data in GitHub Actions cache. Subsequent runs restore it. On a warm cache, a deploy that took 4 minutes cold takes under 40 seconds - because only the changed layers rebuild.

A few more things worth doing

  • Run as a non-root user: add USER node before CMD in your production stage. The node image ships with a node user for exactly this purpose. Running as root in a container is a security risk with no upside.
  • Use .dockerignore: it works like .gitignore and prevents COPY . . from sending node_modules, .git, and test fixtures into the build context. Without it, those get hashed on every build even if they're never used.
  • Pin your base image version: node:20-alpine is fine; node:20.11.1-alpine3.19 is better. Tags like 20-alpine are mutable - the image they point to can change under you. Pinning the patch version makes builds reproducible.

None of this is complex. The Dockerfile above is maybe 30 lines. But the difference it makes - smaller attack surface, faster CI, no dev tooling in production - compounds across every deploy for the lifetime of the project. Worth the 30 minutes to set it up right the first time.
