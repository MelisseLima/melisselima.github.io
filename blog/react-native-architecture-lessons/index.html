Architecture lessons from shipping a production React Native app

What I learned about navigation, state management, and CI/CD after taking a React Native app from zero to the App Store and Google Play.

Shipping a React Native app is one thing. Shipping one that's maintainable six months later - with a small team, real users, and a CI pipeline that doesn't break on a Tuesday - is another thing entirely.

After going through this twice (once at Banco do Brasil, once building FitAI), I've collected a set of decisions I'd make the same way again and a few I'd do differently. Here they are.

Navigation: commit to one approach early

React Navigation is the standard and it's good. The mistake is treating it as an afterthought. Navigation structure bleeds into everything - deep linking, auth guards, analytics, modals, tab state. If you sketch it on a whiteboard before writing a line of code, you'll save yourself a refactor later.

The pattern that worked for me: a root stack with an auth gate at the top, nested navigators per feature (tabs, stacks), and no navigation logic inside screens - that lives in dedicated navigator files.

// Root structure that scales
<NavigationContainer>
  <RootStack.Navigator>
    {isAuthenticated
      ? <AppNavigator />   // tabs + feature stacks
      : <AuthNavigator />  // login / onboarding
    }
  </RootStack.Navigator>
</NavigationContainer>

State management: boring is correct

I've used Redux, Zustand, React Query, and combinations of all three. My current opinion: React Query for server state, Zustand for local UI state, nothing else. Redux is powerful but it's infrastructure. You'll spend real time on it. For most apps, you don't need that trade-off.

The hard part isn't picking a library - it's deciding what counts as "server state" vs "UI state." Server state is anything that lives in a database somewhere and needs to stay in sync. Everything else is UI state. Keep them separate from day one.

If your state management setup requires a tutorial to onboard a new developer, it's too complex.

Performance: profile before you optimise

React Native apps are fast until they're not, and when they're not, the cause is almost never what you expect. In both projects, the performance issues I spent the most time on were:

  • FlatList without proper keyExtractor and getItemLayout - re-renders on every scroll
  • Image loading without caching - react-native-fast-image solves this completely
  • useEffect chains that fire on every render - missing or wrong dependency arrays
  • Heavy work on the JS thread - anything compute-intensive should move to a native module or a web worker via react-native-workers

Flipper's Performance plugin and Hermes' built-in profiler are your friends. Use them before reaching for memoisation - useMemo and useCallback have overhead too, and adding them everywhere without measurement makes things worse.

CI/CD: automate the painful parts

Manual builds are a trap. The first time you miss a signing certificate rotation or ship a build with wrong environment variables, you'll spend the time to automate it. Do that first instead.

My current stack: GitHub Actions for test and lint on every PR, Fastlane for building and signing, and a single command to push to TestFlight and the Play Store internal track. The setup takes two to three days. It pays back within a month.

# .github/workflows/test.yml (simplified)
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - run: npm ci
      - run: npx jest --coverage
      - run: npx eslint src/

The thing nobody talks about: env management

React Native has no standard way to handle environment variables. Everyone does it differently and it causes real problems. The approach I use now: react-native-config for values that change per environment, a .env.example committed to the repo, and actual .env files only on CI via secrets.

Never hardcode a URL. Even if you're 100% sure it won't change, it will change, and you'll need to rebuild and resubmit to the App Store to fix a string.

None of these decisions are revolutionary. The value is making them explicitly at the start of a project rather than discovering them through pain six months in. React Native is a mature platform now - the architecture patterns that work are well understood. Use them.
