Terraform for engineers who just want their app to run

A practical guide to ECS, S3, and CloudFront from someone who came from the application layer and had to learn infrastructure the hard way.

I didn't come up through DevOps. I came through application code - React, Node, mobile - and at some point the team I was on stopped having a dedicated infrastructure person. So I learned Terraform by necessity, not by choice.

What I found is that most Terraform guides are written for people who already think in infrastructure terms. They explain HCL syntax and provider blocks, but they skip the mental model shift that application developers actually need. This post is the one I wish I'd had.

The mental model: Terraform is just a diff tool

Once this clicked, everything else made sense. Terraform doesn't configure your cloud - it describes the desired state of your cloud and reconciles the difference between what you want and what exists. When you run terraform apply, it computes a diff (the plan) and executes only the changes needed.

This means the order of your code mostly doesn't matter. Terraform figures out the dependency graph. It also means you can run terraform plan any time to see exactly what will change - without changing anything. That's your safety net. Use it obsessively before every apply.

Always run terraform plan and read the output before terraform apply. Every time. Even for small changes.

The stack: ECS + S3 + CloudFront

For a standard web app with an API backend and a static frontend, this is the setup I use. It's not the only way, but it's reliable, cost-effective, and well-supported by Terraform's AWS provider.

  • ECS (Fargate) - runs your backend containers without managing EC2 instances
  • S3 - hosts your static frontend build output
  • CloudFront - CDN in front of both, handles HTTPS and caching
  • ECR - stores your Docker images
  • RDS or Aurora - database, if needed

Here's what the folder structure looks like before writing a single resource:

infrastructure/
├── main.tf          # provider config, backend
├── variables.tf     # input variables
├── outputs.tf       # values to export (URLs, ARNs)
├── ecs.tf           # ECS cluster, service, task definition
├── ecr.tf           # container registry
├── s3.tf            # static site bucket
├── cloudfront.tf    # CDN distribution
├── network.tf       # VPC, subnets, security groups
└── iam.tf           # roles and policies

Splitting resources into separate files by service keeps things navigable. One massive main.tf works but you'll regret it when you're searching for a security group rule at midnight.

Start with state - before anything else

Terraform's state file tracks what it has created. By default it lives locally at terraform.tfstate. That's fine for solo experiments. For anything real, store state remotely in S3 with a DynamoDB lock table from day one. Changing this later is painful.

# main.tf
terraform {
  backend "s3" {
    bucket         = "my-app-terraform-state"
    key            = "production/terraform.tfstate"
    region         = "eu-west-1"
    dynamodb_table = "terraform-lock"
    encrypt        = true
  }
}

provider "aws" {
  region = var.aws_region
}

Create the S3 bucket and DynamoDB table manually first (just this once - it's a chicken-and-egg problem). Everything else gets managed by Terraform.

ECS Fargate: the parts that tripped me up

ECS has a lot of moving parts. The mental model: a Cluster is just a logical boundary. A Service maintains N running copies of a Task. A Task is defined by a Task Definition, which is essentially a Docker run configuration.

# ecs.tf (simplified)
resource "aws_ecs_cluster" "main" {
  name = "${var.app_name}-cluster"
}

resource "aws_ecs_task_definition" "api" {
  family                   = "${var.app_name}-api"
  requires_compatibilities = ["FARGATE"]
  network_mode             = "awsvpc"
  cpu                      = 256
  memory                   = 512
  execution_role_arn       = aws_iam_role.ecs_execution.arn

  container_definitions = jsonencode([{
    name  = "api"
    image = "${aws_ecr_repository.api.repository_url}:latest"
    portMappings = [{ containerPort = 3000 }]
    environment = [
      { name = "NODE_ENV", value = "production" }
    ]
    logConfiguration = {
      logDriver = "awslogs"
      options = {
        awslogs-group         = "/ecs/${var.app_name}"
        awslogs-region        = var.aws_region
        awslogs-stream-prefix = "api"
      }
    }
  }])
}

resource "aws_ecs_service" "api" {
  name            = "${var.app_name}-api"
  cluster         = aws_ecs_cluster.main.id
  task_definition = aws_ecs_task_definition.api.arn
  desired_count   = 2
  launch_type     = "FARGATE"

  network_configuration {
    subnets          = var.private_subnet_ids
    security_groups  = [aws_security_group.ecs_tasks.id]
    assign_public_ip = false
  }

  load_balancer {
    target_group_arn = aws_lb_target_group.api.arn
    container_name   = "api"
    container_port   = 3000
  }
}

The two things that confused me most when I started:

  • The execution role vs the task role: the execution role is for ECS itself (pulling images, writing logs). The task role is for your application code (reading S3, calling other AWS services). They're different IAM roles. Don't conflate them.
  • awsvpc network mode: Fargate requires it. Each task gets its own network interface. Security groups apply at the task level, not the instance level. This is good - it means finer-grained control - but it means your SG rules need to explicitly allow inbound from your load balancer.

S3 + CloudFront for static sites

The pattern is straightforward but has a gotcha around bucket access. The current best practice is Origin Access Control (OAC), not the older Origin Access Identity (OAI). Keep the S3 bucket private - CloudFront accesses it via OAC, users never hit S3 directly.

# s3.tf
resource "aws_s3_bucket" "frontend" {
  bucket = "${var.app_name}-frontend"
}

resource "aws_s3_bucket_public_access_block" "frontend" {
  bucket                  = aws_s3_bucket.frontend.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# cloudfront.tf
resource "aws_cloudfront_origin_access_control" "frontend" {
  name                              = "${var.app_name}-oac"
  origin_access_control_origin_type = "s3"
  signing_behavior                  = "always"
  signing_protocol                  = "sigv4"
}

resource "aws_cloudfront_distribution" "frontend" {
  origin {
    domain_name              = aws_s3_bucket.frontend.bucket_regional_domain_name
    origin_id                = "s3-frontend"
    origin_access_control_id = aws_cloudfront_origin_access_control.frontend.id
  }

  enabled             = true
  default_root_object = "index.html"

  default_cache_behavior {
    allowed_methods        = ["GET", "HEAD"]
    cached_methods         = ["GET", "HEAD"]
    target_origin_id       = "s3-frontend"
    viewer_protocol_policy = "redirect-to-https"

    forwarded_values {
      query_string = false
      cookies { forward = "none" }
    }
  }

  # SPA routing  - serve index.html for 404s
  custom_error_response {
    error_code         = 404
    response_code      = 200
    response_page_path = "/index.html"
  }

  restrictions {
    geo_restriction { restriction_type = "none" }
  }

  viewer_certificate {
    acm_certificate_arn = var.acm_certificate_arn
    ssl_support_method  = "sni-only"
  }
}

The custom_error_response block is critical for SPAs - without it, any direct URL hit that isn't the root will return a 403 from S3. Your React Router or Next.js routes will silently break in production.

Deploying new code without Terraform

This is the thing nobody explains clearly: Terraform manages infrastructure, not application deployments. Once your ECS service and CloudFront distribution exist, you don't re-run Terraform to push new code.

For ECS, a new deploy is: build a new Docker image → push to ECR → force a new ECS service deployment. For the frontend, it's: build → sync to S3 → invalidate CloudFront cache. Both of these belong in your CI pipeline, not in Terraform.

# CI deploy commands (GitHub Actions / CircleCI / etc.)

# Backend
docker build -t $ECR_REPO:$COMMIT_SHA .
docker push $ECR_REPO:$COMMIT_SHA
aws ecs update-service \
  --cluster my-cluster \
  --service my-api \
  --force-new-deployment

# Frontend
npm run build
aws s3 sync dist/ s3://my-frontend-bucket --delete
aws cloudfront create-invalidation \
  --distribution-id $CF_DISTRIBUTION_ID \
  --paths "/*"

Infrastructure as code pays for itself the first time you need to recreate an environment - staging parity, disaster recovery, or just onboarding a new developer. The initial investment is real, but you stop being afraid of your own cloud setup. That's worth a lot.
